# 兼容性与数据含义

## 支持范围

| 项目 | 当前实现 / 边界 |
| --- | --- |
| 机器人 | G1 EDU 29 自由度身体，左右 Dex3 各 7 关节；其他型号未验证 |
| 宿主目标 | Ubuntu 22.04 / 24.04，原生 Docker Engine；尚未声称在另一台全新电脑上完成实机验收 |
| 独立运行环境 | Ubuntu 22.04 Docker 镜像，CycloneDDS 0.10.2、Unitree Python SDK；版本以 Dockerfile 为准 |
| 浏览器 | 支持 WebGL 2 和 ES module 的现代浏览器，静态资源本地提供 |
| ROS | 正常运行无需安装 ROS；点云使用标准 ROS 2 DDS 消息布局，不启动 ROS 节点 |
| 网络 | 选定网卡具有 IPv4，能发现 DDS 发布端并接收数据；通常为有线同网段，也可由实际网络配置提供路由 |

开发版本曾在一台 G1 EDU 29 + 双 Dex3 + MID-360 上检查身体、双手、设备状态、点云与前置视频。不同硬件、消息版本、固件、话题和网络仍需分别核对；单元测试、演示或 Docker 构建成功不代表完成另一台机器人的验收。

## 身体与双手

身体使用 `rt/lowstate` 的前 29 个关节角；骨盆 IMU 四元数按 `wxyz` 顺序处理。模型固定骨盆位置，仅显示姿态，不是里程计或定位结果。

`mode_pr=0` 时按 PR 关节坐标映射；`mode_pr!=0` 时不把 A/B 并联电机角直接套入模型，身体显示灰色零位参考并提示映射停用，原始数据仍可读取。`mode_machine`、`motorstate` 保留原值，不自动诊断故障。

双手分别订阅 `rt/dex3/left/state` 和 `rt/dex3/right/state`，每手 7 关节。左手序号 3/4 映射中指、5/6 映射食指。右手默认同样使用 `middle-first`，依据开发时用户对一台实机的现场校正；它与部分官方枚举的右手顺序不同，不能视为所有固件的统一定义。

```bash
./run.sh --interface enp3s0 --right-hand-order index-first
```

若右手侧指反了，可改用上述选项并对照实机。程序直接使用测量角度，不自动取反或补偿零点。模型外观也可能与实际附件不同。

## MID-360 点云

默认话题 `rt/utlidar/cloud_livox_mid360`，DDS 类型 `sensor_msgs::msg::dds_::PointCloud2_`。可通过 `--lidar-topic` 修改话题。默认 reliable 接收，发布端为 best-effort 时需使用 `--lidar-best-effort`。

解析支持 float32 / float64 XYZ、有组织点云、行填充和大小端；排除 NaN、Infinity 及零距离点。默认接收 50 米内最多 50,000 点；网页短时叠加最多绘制 100,000 点。点云在自己的 `frame_id` 下显示，不自动变换到机器人模型坐标，也不做建图或运动补偿。

页面提供单帧、0.3 秒和 0.6 秒窗口。叠加可能造成运动重影。后端缓冲同时间戳样本时优先较大的完整帧，不用旧帧伪装为新接收。显示频率取决于发布端、QoS、消息大小、丢包和处理耗时；不承诺固定帧率。

## 电池、主板与 FSM

- 电池来源 `rt/lf/bmsstate`。SOC 显示百分比；电压、电流、电芯、温度、SOH 等保留消息原始字段，未核实的单位 / 缩放不换算。
- 主板来源 `rt/lf/mainboardstate`，温度、风扇、数值与状态按原字段展示；不猜测未知槽位的物理含义。
- 温度总览分别显示身体与每只手的最高电机温度，不代表“整机温度”，也不把缺失数据当作零温度。
- 运动模式来源 `rt/sportmodestate`，显示 FSM ID、FSM mode、任务编号和时长。已知名称来自官方 SDK；未知值显示“未映射模式”。FSM 是控制器报告，不是对实际动作的视觉识别。

## 前置视频

话题为 `rt/frontvideostream`，类型名 `unitree_go::msg::dds_::Go2FrontVideoData_`。接收器针对开发时核对的固件布局：

```text
time_frame: uint64
resolution: uint16
data: sequence<uint8>
```

部分旧 SDK 使用三个分辨率数组字段；仅有相同 DDS 类型名不能保证线格式兼容。当前接收器选取 `resolution=360` 的 H.264 分支，等待流头和关键帧，输出 640×360 JPEG，避免不同分辨率包混入同一个解码器。

视频通过 `ctypes` 调用 FFmpeg 共享库，**要求 ABI `avcodec=58`、`avutil=56`、`swscale=5`**，并使用 NumPy / OpenCV。独立镜像选择相应 Ubuntu 22.04 库；直接在其他 Python / 系统环境运行时，较新的 FFmpeg ABI 可能不匹配。ABI 不符会报错，不会继续使用不匹配的结构体。

单包最多 8 MiB，解码尺寸最多 4096×2160，使用 32 包 FIFO 顺序解码。视频缺少有效图像时 `/api/video/frame` 返回 204；过期图像不继续展示。只有内存中最近一张图像，不录音、不录像、不打开相机服务、不上传云端。

视频不兼容不等于其他状态通道不兼容。机器人未发布该话题、消息结构不同、未收到关键帧或 ABI 不匹配时，可继续查看正常的身体 / 手部 / 点云状态。

## 独立通道与新鲜度

身体、左右手、雷达、电池、运动模式、主板和视频分别缓存与计数。两秒未收到有效数据时显示过期。`matched` 是已匹配发布者数量，`rejected` 是解析 / 处理异常计数；已匹配并不说明收到可用样本。接收频率是本程序处理到的频率，不是机器人或传感器的标称频率。

应用只创建读取状态所需的 DDS 实体，不建立控制发布者，不调用运动、模式切换、雷达开关或相机开关服务。`tests/` 的模拟发布者用于隔离测试，固定使用 loopback 与隔离 domain，不属于正常启动流程。
